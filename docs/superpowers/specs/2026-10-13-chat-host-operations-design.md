# personal-ops-tunnel 채팅 기반 호스트 작업 확장 설계

- 날짜: 2026-10-13
- 상태: 사용자 설계 확인 완료(2026-10-13, “진행”). 구현 계획 작성 단계다. 신규 기능은 아직 구현하거나 활성화하지 않았다.
- 저장소: `personal-ops`, 구현 영역: `chatgpt-mcp/`
- 확정된 사용자 선택: 작업 요청과 실행·결과 확인은 터널 채팅에서, 최종 승인은 기존 관리 웹에서 진행한다.
- 추가 사용자 요구: MCP 기능으로 완료할 수 없는 작업은 관리 웹에서 범위를 승인받고 호스트 코딩 에이전트에 위임할 수 있도록 설계한다.
- 현재 실행 경계: 기존 Docker 컨테이너와 DB 데이터를 변경하지 않는다. Schema 013 적용 승인은 별도 단계로 남긴다.

## 1. 목표와 완료 기준

사용자가 일반 ChatGPT 채팅에서 `personal-ops-tunnel`을 선택하고, 등록된 프로젝트의 파일 편집, 명령·빌드·테스트 실행, Docker 서비스 관리, DB 조회·변경, 마이그레이션 적용 및 적용 결과 확인까지 이어서 수행할 수 있도록 확장한다. 기본 경로는 기존 MCP가 직접 실행하며, 기능 부족으로 완료할 수 없는 작업은 별도로 승인한 호스트 코딩 에이전트에 위임할 수 있다.

완료된 흐름에서는 채팅이 구체적인 작업 계획과 승인 링크를 제공한다. 사용자가 관리 웹에서 영향과 입력을 확인해 승인하면 채팅에서 해당 작업을 실행하고 진행 단계·성공 여부·실제 대상 상태를 확인한다. 채팅을 새로 열어도 프로젝트와 작업 ID로 기존 작업을 조회하며, 승인 또는 실행을 중복하지 않는다.

```text
ChatGPT + MCP
      |
      +--> Repo files / sandbox jobs --> Result
      |
      +--> Frozen host plan --> Admin web approval
                                    |
                     One-use receipt + revalidation
                                    |
                         Docker / PostgreSQL adapter
                                    |
                         Events + postcheck --> ChatGPT

Capability gap --> Agent task plan --> Admin web approval
                                              |
                                   Dedicated CLI agent job
                                              |
                             Repo work + approved host broker
                                              |
                                    Result --> ChatGPT
```

등록된 프로젝트와 호스트 대상만 허용한다. 소스 구현의 승인, 대상 설정의 활성화 승인, 개별 Docker·DB 작업 승인은 서로 다른 범위다. 이 문서는 기존 대상 설정을 변경하거나 실제 작업을 승인한 기록이 아니다.

## 2. 현재 기능과 확장 지점

| 작업 | 현재 상태 | 이 설계의 변경 |
| --- | --- | --- |
| 프로젝트 선택·파일 조회·편집 | 허용 로컬 저장소에서 가능 | 기존 도구와 경로 검사 재사용 |
| 명령·빌드·테스트 | `start_command`의 격리 환경에서 가능 | 기존 작업 ID·로그 커서·취소 기능 재사용 |

| Docker 조회·배포 | `tossApp/tarororo-test` API·Worker의 고정 작업 | 등록된 Compose 대상과 동작으로 확장 |
| 기존 DB 마이그레이션 | 정확한 013 전용 계획·실행 경로 | 범위가 고정된 배치, SQL 작업, 백업·복구 추가 |

| 작업 상태 | 승인·큐·실행·검증 상태 저장 | 일반 작업의 단계·안전한 이벤트와 복구 조회 확장 |
| Git 작업 | commit/push는 별도 승인, PR/merge는 기존 워크플로우 | 기존 계약을 유지하며 호스트 작업 승인과 합치지 않음 |
| 승인된 에이전트 위임 | 관측용 CLI adapter는 있으나 호출 도구 없음 | 전용 CLI 작업의 계획·승인·실행·결과·취소 추가 |

기준 파일은 `chatgpt-mcp/server.py`, `execution.py`, `jobs.py`, `host_runtime_config.py`, `host_runtime_tools.py`, `host_runtime_operations.py`, `host_runtime.py`, `host_db_migration.py`, `host_runtime_web.py`, `admin_server.py`, `admin.js`다.

2026-10-13 선행 진단에서 `tarororo-test` DB는 001–005 이력과 체크섬이 일치했고 006–012와 013은 미적용이었다. 이는 당시 관측 결과이며 실행 계획 작성 시 다시 조회한다. `tossApp`의 일반 마이그레이션 실행기는 누락된 006–013을 모두 시도하므로, 이를 006–012 전용 명령으로 취급하지 않는다.

## 3. 접근 방식 선택

| 방식 | 장점 | 비용·제약 | 결정 |
| --- | --- | --- | --- |
| 기존 MCP에 대상 등록·정형 작업 어댑터 추가 | 현재 승인·작업 상태 재사용, 추가 모델 호출 없이 실행 | 동작별 입력·사후 검사 구현 필요 | 기본 경로 |
| 승인된 Codex/Claude CLI 에이전트 위임 | 복잡한 작업을 묶어 진행하고 코딩 에이전트 도구를 사용 | 별도 모델 사용량·작업 세션·권한 격리 필요 | 기능 부족 시 선택 경로 |
| 채팅에서 임의 호스트 셸 실행 | 명령 표현이 자유로움 | 프로젝트와 승인 영향의 경계를 보장하기 어려움 | 채택하지 않음 |

일반 명령은 기존 샌드박스에서 실행한다. 호스트 접근이 필요한 작업은 등록된 대상의 Docker·DB 어댑터로 실행한다. 샌드박스 실행이 실패했다는 이유로 호스트 셸에 자동 전환하지 않는다.

에이전트 위임도 자동 전환하지 않는다. 채팅이 이유와 범위를 제시하고 운영자가 웹에서 승인해야 시작한다. 에이전트 권한은 등록된 실행 프로필이 정하며 기존 기능의 거부 조건을 우회하는 경로가 아니다.

## 4. 대상 설정과 호환성

기존 비공개 `host-runtime.json`을 version 3으로 확장한다. version 1·2 파일과 기존 7개 MCP 도구의 동작은 유지한다. version 3을 활성화하지 않은 설치에서는 새 쓰기 권한이 생기지 않는다.

각 대상은 다음 정보를 호스트에서 설정한다.

- 허용 프로젝트 이름과 등록된 로컬 저장소의 정체성. 경로는 `projects.json`에서 가져온다.
- 대상 ID, `test` 환경 구분, Compose 파일·프로젝트 이름·서비스 목록, 허용 포트·네트워크·마운트·볼륨.
- 허용 동작 목록, 컨테이너 실행 프로필, DB 이름·엔진·연결 방식·역할의 정체성.
- 자격 증명과 백업 저장소의 호스트 측 참조. 비밀 값이나 DB URL을 MCP 인자로 받지 않는다.
- 소스 검토 정책, 보호할 마이그레이션 목록, 승인 웹 주소, 설정 지문.

초기 등록 후보는 기존 `tossApp/tarororo-test`뿐이다. 다른 저장소가 파일 편집 목록에 있다는 사실은 Docker·DB 권한을 부여하지 않는다. 운영 환경 등록은 이 릴리스의 범위에서 제외한다.

설정·작업 상태·승인 영수증·백업은 편집 가능한 저장소 밖에 둔다. 개인 디렉터리는 0700, 개인 파일은 0600이며 소유자와 심볼릭 링크를 검사한다. 현재 설정의 해석에 실패하면 권한을 닫고 제한된 오류를 반환한다.

## 5. 작업 계약과 신규 MCP 인터페이스

다음 도구를 추가한다. 기존 조회·013 전용·API/Worker 배포 도구는 유지한다.

| 도구 | 입력 | 결과·효과 |
| --- | --- | --- |
| `list_host_targets` | `project` | 등록된 대상과 활성 기능, 제한 사유 조회 |
| `inspect_host_target` | `project`, `target`, 등록된 조회 영역 | Docker 정체성·건강 상태, DB 역할·스키마 메타데이터 조회 |
| `prepare_host_operation` | `project`, `target`, `action`, 정형 `parameters`, `request_id` | 입력을 고정한 계획 생성. Docker·SQL 실행 없음 |
| `execute_host_operation` | `project`, `target`, `operation_id` | 해당 계획의 웹 승인 영수증을 소비하고 비동기 실행 |
| `read_host_operation_events` | `project`, `target`, `operation_id`, `cursor`, 제한 | 안전한 단계 이벤트를 커서로 조회 |

기존 `get_host_operation`은 version 3 작업도 조회하도록 내부 라우팅을 확장한다. version 1·2의 정확한 대상 검사와 응답은 유지한다. 도구 입력은 미등록 필드·대상·동작을 거절한다. Docker 소켓 경로, DB URL, 백업 절대 경로, 임의 호스트 환경변수는 클라이언트 입력에 없다.

계획은 동작·정규화한 인자·대상 정체성·소스 스냅샷·설정 및 실행기 지문·예상 영향·검증 항목·만료 시각·무작위 nonce를 포함한다. `plan_digest`는 승인 내용을 묶는다. 같은 요청 ID와 같은 입력은 같은 계획을 반환하고, 같은 요청 ID의 다른 입력은 거절한다.

계획은 한 가지 동작 또는 명시적으로 고정한 하나의 마이그레이션 배치만 포함한다. Docker 배포와 DB 적용을 암묵적으로 묶지 않는다. 마이그레이션 범위와 실행 순서를 승인을 받은 뒤 확대할 수 없다.

계획·승인은 시작 전까지 10분 동안 유효하다. 실행이 시작된 뒤에는 TTL 때문에 자동 재실행하거나 중단하지 않고 작업별 timeout을 적용한다. DB 결과는 최대 100행·64 KiB, 이벤트 조회는 기본 50건·최대 200건·64 KiB로 제한한다. 명령 출력 수집은 기존 256 KiB 상한을 유지하며, 공개 출력은 위의 제한된 메타데이터뿐이다.

## 6. Docker 작업

등록된 Compose 서비스에 대해 상태·건강 상태·이미지 정체성 조회, 빌드, 이미지 적용, 기동, 재기동, 중지 및 등록된 실행 프로필을 지원한다. 모든 상태 변경과 컨테이너 내부 명령 실행은 개별 승인 계획을 사용한다.

- 빌드 입력은 `.dockerignore`, Dockerfile, Compose, 실제 컨텍스트와 의존 파일까지 스냅샷으로 고정한다. 작업별 이미지 태그와 image ID를 기록한다.
- 적용은 승인한 서비스만 대상으로 한다. `--no-deps --no-build --pull never`와 검증된 override를 사용하며, 다른 서비스의 교체가 필요하면 새 계획을 요구한다.
- 재기동·중지 계획은 중단될 서비스와 DB 연결 영향을 표시한다. DB 서비스 동작은 별도의 DB 서비스 권한을 요구한다.
- `compose.exec`는 호스트 설정의 실행 프로필을 선택한다. 프로필별 실행 파일·인자·작업 디렉터리와 코드 입력을 검증한다. 모델이 임의 호스트 셸을 지정할 수 없다.
- `compose.down`은 별도 권한과 전체 대상 영향 승인을 요구하고 볼륨을 보존한다. `down -v`, 전역 `prune`, 볼륨 삭제는 이번 범위에서 제외한다.
- 컨테이너 소켓 마운트, 호스트 루트 마운트, 승인되지 않은 호스트 경로·네트워크·특권 옵션은 계획 단계에서 거절한다. 승인 버튼으로 이 정책을 해제할 수 없다.

작업 후 예상 서비스의 image ID·상태·health 및 보호 대상 컨테이너의 세대를 확인한다. 결과를 확인할 수 없으면 성공으로 보고하지 않는다. 자유 형식 컨테이너 로그는 기본적으로 MCP에 내보내지 않고, 등록된 형식에서 추출한 단계·오류 코드·건수만 제공한다.

## 7. PostgreSQL 조회·변경·스키마 적용

DB 어댑터는 PostgreSQL부터 구현한다. 다음 작업은 호스트에 등록된 정확한 DB만 대상으로 한다.

- `db.inspect`: DB·역할 정체성, 테이블·컬럼·migration history 등 고정된 읽기 전용 메타데이터 검사.
- `db.query`: 저장소 안의 SQL 파일을 고정해 승인받고 제한된 읽기 전용 세션에서 실행. 반환 허용 컬럼·행 수·바이트 상한도 계획에 포함한다. 기본 출력은 결과 건수·검증 메타데이터다.
- `db.execute`: 승인된 SQL 파일의 데이터 변경 실행. 대상 설정에서 허용한 테이블·동작에 맞는 전용 역할을 사용한다. DDL은 마이그레이션 배치로 실행한다. 영향 요약·백업·사후 SQL 검사도 승인 내용에 포함한다.
- `db.migrate`: manifest에 나열한 파일의 정확한 순서·SHA-256·현재 이력·목표 범위를 고정한 배치 실행.
- `db.backup`: 등록된 비공개 백업 저장소에 백업 생성 후 복원 검증. 파일 원문이나 자격 증명을 채팅에 반환하지 않는다.
- `db.restore`: 검증된 백업 ID와 대상 DB를 고정한 별도 복구 계획. 기존 데이터를 바꾸는 영향과 서비스 중단·재연결 절차까지 승인받는다. 실패 후 자동 복구하지 않는다.

범용 SQL은 비-superuser이며 다른 DB·역할 변경 및 서버 OS 접근 권한이 없는 등록 역할에서만 실행한다. 역할 권한을 사전 검사하고 충족하지 않으면 해당 기능을 비활성으로 보고한다. 역할 생성·권한 부여는 자동 수행하지 않는다. 기존 013 전용 경로의 정확한 SQL·대상 제한은 유지하며 범용 SQL 권한으로 해석하지 않는다.

SQL 파일을 임의 `psql -f` 또는 프로젝트의 수정 가능한 마이그레이션 스크립트로 실행하지 않는다. 신뢰된 실행기에서 SQL 본문을 전송하고, psql 메타 명령·셸 실행 경로를 허용하지 않는다. SQL 정규식 검사만으로 권한 안전성을 보장한다고 주장하지 않는다.

DDL·데이터 변경 전에는 실제 대상의 역할·DB 정체성, 현재 schema fingerprint와 이력 체크섬, 승인 SQL·검증 파일의 바이트를 다시 확인한다. 변동 시 `STALE_PLAN`으로 중단한다. DB 변경은 검증된 백업과 격리된 복원 검사에 성공한 뒤 실행하며, 백업용 임시 자원도 작업 계획에 표시한다.

기본 실행은 transaction, statement/lock timeout, DB 측 advisory lock을 사용한다. SQL 세션의 search path와 클라이언트 초기화 옵션은 실행기가 고정한다. 트랜잭션 밖 작업이 필요한 SQL과 임의 transaction-control 문은 이 릴리스에서 거절한다. 지원하는 SQL 형식의 lexer 검증과 역할 권한 검사를 모두 통과해야 실행하며, 해석하지 못하는 입력을 그대로 넘기지 않는다. DB 소유권·접속 상태에 따라 전체 DB 복구가 불가능하면 `RESTORE_PREREQUISITE_MISSING`을 반환하고 컨테이너 종료나 세션 강제 종료를 대신 시도하지 않는다.

### Schema 013의 분리

`tossApp/tarororo-test`의 `013_staged_reading_access.sql`은 보호 목록에 둔다. 일반 `db.migrate` 배치에는 포함할 수 없고, 기존 `prepare_db_migration`을 통해 별도 승인·실행한다. 일반 SQL 작업이 이 보호 범위를 우회하는 용도로 사용되지 않도록 해당 대상의 쓰기 권한은 호스트에서 등록한 파일·SHA-256·검증 프로필에 한정한다. DML 역할에는 DDL·migration history 변경 권한을 주지 않는다. 파일 이름만 검사하면 우회할 수 있으므로 범용 SQL 전체를 이 대상에 열지 않는다.

006–012 계획은 일곱 파일, 순서, 각 SHA-256, 기존 001–005 이력, 예상 테이블·이력 결과를 고정한다. 기존 이력을 임의 삽입해 미적용 SQL을 적용된 것으로 표시하지 않는다. 006–012 완료가 013 승인으로 이어지지 않는다.

보호할 013의 이력·관계·스키마 정체성은 배치 계획과 복원 검사에도 포함한다. 배치는 격리 복원본에서 먼저 검증하고 실제 트랜잭션의 commit 전에 보호 상태가 유지되는지 다시 검사한다. 복구 계획은 검증한 백업의 보호 상태가 현재 대상과 같을 때만 허용한다. 다르면 별도 013 승인 경로로 돌려보내고 복구를 실행하지 않는다.

## 8. 소스 변경과 검토

기존 version 1·2의 고위험 파일 Git HEAD 검사는 유지한다. 미커밋 입력을 허용하려면 version 3 대상에서 별도 `reviewed_snapshot` 정책을 명시적으로 활성화해야 한다. 단순히 Git HEAD 검사를 제거하거나 자동 커밋해 통과시키지 않는다.

이 정책에서는 계획 시점에 실제 입력의 private snapshot을 만들고, 관리 웹에서 실행 제어 파일·SQL과 Git HEAD 대비 변경 내용을 검토할 수 있게 한다. 승인 영수증은 해당 snapshot digest에 묶인다. 실제 실행은 그 스냅샷만 사용하고, 현재 소스나 대상이 승인 후 바뀌면 새 계획을 요구한다. 스냅샷에 `.env`, `.git`, 등록되지 않은 외부 파일 또는 경로 밖 심볼릭 링크를 포함하지 않는다. 비밀은 별도로 검증한 호스트 참조로 제공한다.

Git commit은 소스 식별 정보이며 실제 웹 승인 영수증을 대신하지 않는다. 반대로 이 정책은 Git commit/push 승인이나 PR 검토를 대체하지 않는다.

## 9. 관리 웹 승인 흐름

채팅에는 대상·동작·서비스 또는 migration 범위·예상 영향·계획 만료와 승인 링크를 보여 준다. 링크에는 프로젝트와 작업 ID만 넣고 인증 토큰·nonce·비밀을 포함하지 않는다.

관리 웹에서 운영자가 다음 내용을 확인한다.

1. 프로젝트·대상·환경과 현재 대상 정체성.
2. 실행할 동작·인자·고정한 입력 파일·변경 검토 자료.
3. 컨테이너 교체·중단·DB 변경·복구의 영향과 보호할 대상.
4. 백업·복원 검사·사후 검사와 실패 시 처리.
5. 정확한 계획 digest·만료 시각과 승인 또는 거절.

인증, Origin 검사, 신뢰된 승인 주소 검사는 기존 `host_runtime_web.py`와 `admin_server.py`에서 재사용한다. 현재 LAN HTTP 주소는 조회용이며 쓰기 승인 경로로 자동 확대하지 않는다. 폰에서는 기존 Tailscale HTTPS 경로를 사용하고, PC 승인도 신뢰된 HTTPS 경로 또는 호스트 loopback을 사용한다. 새 HTTPS/LAN 승인 경로가 필요하면 별도 호스트 설정 작업으로 다룬다.

승인 버튼은 작업 실행을 시작하지 않는다. 서버가 인간의 인증된 승인 요청에서 1회 영수증을 발급하고, 채팅은 승인된 작업 ID로 실행을 요청한다. MCP 인자의 `approved=true`, 모델이 전달한 토큰, UI 도구 visibility 또는 도구 annotations는 승인 근거가 아니다.

현재 릴리스는 ChatGPT iframe에 승인 인증을 넣지 않는다. 서버가 작업 상태와 링크를 반환하므로 ChatGPT의 특정 카드 표시 여부에 의존하지 않는다.

## 10. 실행·장애·관찰

```text
pending_host_approval --> approved --> queued --> running
           |                 |                     |
           +--> rejected     +--> expired          +--> succeeded
           +--> expired                            +--> failed
                                                   +--> outcome_unknown

running phases: PRECHECK --> BACKUP --> EXECUTE --> VERIFY
```

위 도식은 주요 경로다. 동작에 필요 없는 단계는 건너뛰고 복원 검사는 BACKUP 단계에 포함한다. 검증 중 상태는 기존 계약과 같은 `running`이며 phase로 구분한다. 실행 중 어느 단계에서도 확실히 확인한 실패는 `failed`, 실제 효과를 확인하지 못하면 `outcome_unknown`으로 종료한다. 승인 대기 중 만료도 `expired`로 처리한다.

대상 lock과 DB advisory lock으로 같은 대상의 충돌 작업을 막는다. 승인 영수증은 소비 후 재사용할 수 없다. 재전송은 기존 작업을 조회하며, timeout·터널 끊김·런타임 재시작 후 상태 변경 작업을 자동 재실행하지 않는다.

Docker 명령 프로세스 종료가 데몬 작업 종료를 뜻하지 않으며, DB 클라이언트 종료만으로 변경 여부를 단정할 수 없다. 별도의 읽기 전용 reconciliation에서 컨테이너 세대·image ID·migration history와 검증 결과를 확인하고 증거가 충분할 때만 결과 상태를 정리한다.

이벤트는 단조 증가 cursor, 시각, phase, 제한된 event code·진행 건수·검증 결과를 포함한다. stdout/stderr 원문, DB URL, 자격 증명, 애플리케이션 데이터, 프롬프트·추론 원문을 감사 로그에 저장하지 않는다. DB 오류는 SQLSTATE와 실패한 승인 파일의 상대 경로를 제공한다. 미확인 오류는 안전한 오류 코드와 진단 ID로 표시한다.

관리 웹에는 승인 대기·실행 중·검증·완료 항목과 최근 이벤트를 표시한다. 채팅에서는 짧은 도구 호출과 상태 조회를 사용한다. ChatGPT 앱의 응답 렌더링이나 모델의 최종 답변 생성을 서버가 보장한다고 주장하지 않는다.

## 11. 구현 범위와 활성화 순서

1. 기존 정책을 재사용하는 작업 계약·대상 registry·어댑터와 관리 웹 확장 소스를 구현한다. 현재 설정·서비스·Docker·DB는 변경하지 않는다.
2. 모의 실행기와 비공개 임시 상태로 회귀·거부 경로를 검증한다. 실제 DB 통합 시험은 명시적으로 정한 폐기 가능한 DB만 사용한다.
3. 독립 코드·권한 경계 리뷰 후 불변 runtime candidate와 기존 설치 대비 차이를 준비한다.
4. 실제 호스트 런타임 반영 및 version 3 대상 설정 활성화는 구체적인 차이와 영향에 대한 별도 승인을 받아 진행한다.
5. 실제 MCP 도구 등록·런타임 manifest·관리 웹·읽기 전용 대상 조회를 검증한다.
6. 실제 Docker·DB 변경은 이 단계들을 통과한 뒤에도 개별 작업 계획과 웹 승인을 요구한다. Schema 013은 마지막까지 별도 승인이다.

새 라이브러리, 별도 상시 에이전트 서비스, 새 터널, 공개 관리 서버는 추가하지 않는다. 에이전트 위임 시에만 이미 설치된 CLI로 모델을 호출한다. 기존 Docker 이미지·컨테이너·DB 데이터를 이 기능의 시연을 위해 변경하지 않는다.

## 12. 검증 계약

- version 1·2 설정, 기존 7개 도구·샌드박스·Git 승인 회귀를 검증한다.
- 미등록 대상·서비스·역할·동작, 경로 탈출·심볼릭 링크, 비밀 인자, 특권 Compose 옵션은 계획 단계에서 거절한다.
- 거절·미승인·만료·변조·재사용 영수증은 상태 변경 실행 횟수가 0인지 검사한다.
- 승인 전후 소스·설정·실행기·컨테이너 세대·DB 이력 변경은 `STALE_PLAN`이며 쓰기 실행이 없어야 한다.
- 같은 요청·같은 실행의 재전송, 병렬 프로세스·대상 lock, 재시작·timeout·불확실 결과에서 중복 실행을 막는다.
- Docker 적용이 승인한 서비스만 변경했는지 검사하고, 다른 서비스·볼륨을 보호한다.
- DB 역할 검사 실패, 백업·복원 검사 실패, SQL 실패·lock timeout에서 적용을 중단한다. 결과 건수와 체크섬·사후 검증은 실제 관측으로 확인한다.
- 006–012 배치가 013을 포함하지 않고 일반 SQL 경로로 보호 범위를 우회할 수 없는지 검증한다. 이력 조작이나 전체 `db:migrate` 실행으로 대체하지 않는다.
- 실제 DB 시험은 폐기 가능한 전용 대상에서 rollback·이력·복원 결과를 확인한다. 기존 `tarororo-test`를 회귀 시험 대상으로 사용하지 않는다.
- 웹의 unauthenticated·foreign Origin·LAN HTTP 승인 요청 거부, 승인 내용 표시, 링크로 작업 재조회, 이벤트 cursor·오류·빈 상태를 검사한다.
- 실제 활성화 후에는 runtime manifest·프로세스 정체성, connector 도구 목록과 실제 읽기 전용 호출, 관리 웹 asset·API 일치 여부를 확인한다. 설정 파일이나 passive discovery 상태만으로 성공을 선언하지 않는다.

- 에이전트 호출은 기본 비활성이어야 하며, 승인 누락·만료·변조·재전송에서는 CLI 시작 횟수가 0 또는 기존 단일 작업 조회인지 검증한다.
- 사용자가 열어 둔 CLI·폰 공유 세션은 건드리지 않는다. 전용 작업의 PID 세대·프로세스 그룹·CLI session ID를 검사한 뒤 취소하고, 전체 `codex`·`claude` 프로세스를 종료하지 않는다.
- 에이전트가 지정하지 않은 레포·호스트 설정·Docker 소켓·DB 자격 증명에 접근할 수 없는지 실제 실행 프로필의 격리 경계를 검증한다. CLI 옵션이나 프롬프트만 검사해서 합격으로 처리하지 않는다.
- CLI 모델 응답의 성공 주장과 실제 파일·검증 결과를 구분하고, 실패·사용 한도·timeout·출력 누락·미확인 모델/usage를 그대로 표시한다.
- 기존 Docker·DB 및 Schema 013 승인 경계를 에이전트 경로에서도 동일하게 검증한다. 실제 계정으로 모델을 호출하는 smoke는 작업·모델 사용량에 대한 명시적 승인 후에만 수행한다.

## 13. 승인된 코딩 에이전트 위임

### 발동 조건과 실행 범위

에이전트가 유용한 경우는 필요한 코딩 도구가 MCP에 없거나, 여러 파일·검사·수정 단계의 복잡한 작업을 하나의 전용 작업으로 맡기려는 경우다. 실행 환경 문제는 승인할 프로필에 실제 필요한 자원이 있는지 확인해야 한다. 에이전트 호출 자체가 누락된 Chromium·PostgreSQL·네트워크·권한을 만들어 주지 않는다.

채팅은 기능 부족 사유, 미완료 작업, 이미 실행한 단계와 효과를 설명한 뒤 계획을 만든다. `POLICY_DENIED`, `UNSUPPORTED_SCOPE`, 승인 누락, 비밀 접근 차단, `STALE_PLAN`은 위임으로 우회하지 않는다. 이전 실행이 `outcome_unknown`이면 먼저 읽기 전용으로 효과를 확인하고, 확인되지 않은 Docker·DB 작업을 에이전트로 다시 시도하지 않는다.

에이전트는 지정된 프로젝트의 파일 작업·빌드·테스트를 수행한다. Docker·DB 변경은 같은 승인 broker를 통해 정확한 작업 계획을 만들고 별도 승인을 받아 실행한다. 해당 호스트 동작의 어댑터나 허용 프로필이 없으면 에이전트도 제한 사유와 추가 구현·설정안을 보고한다. 이 설계는 승인 한 번으로 임의 호스트 명령 전체를 허용하는 기능이 아니다.

| --- | --- |
| `list_agent_profiles` | 허용 프로젝트의 설치된 CLI·모델 프로필·실행 권한·제한 사유 조회 |
| `prepare_agent_task` | 목적·범위·입력 스냅샷·프로필·모델·시간 제한·반영 정책을 고정한 계획 생성 |
| `start_agent_task` | 해당 계획의 1회 웹 승인 영수증을 소비하고 전용 작업 시작 |
| `get_agent_task` | 상태·모델 정보·사용량·안전한 진행 이벤트·변경 파일·검증·남은 승인 조회 |
| `cancel_agent_task` | 검증된 해당 작업 프로세스만 중지. 이미 발생한 효과의 원복은 하지 않음 |

MCP는 프로젝트 이름·등록 프로필과 작업 명세를 받으며 임의 CLI 실행 파일·flags·auth 파일·host environment·기존 세션 ID를 받지 않는다. 승인 화면에는 위임 이유와 작업 목표, 접근할 프로젝트와 대상, 허용 파일·동작, CLI·모델·추론 설정, 최대 실행 시간 및 추가 모델 사용량이 생긴다는 사실을 표시한다.

기본 시간 제한은 30분이며, 입력 계약은 1–60분만 허용한다. 기존 계획과 같이 승인·시작 전 TTL은 10분, 중복 요청과 실행은 같은 작업 ID에 묶는다. 최종 결과는 요약, 변경한 파일, 실행한 검증과 결과, 미완료 사항 및 추가 승인 필요를 포함한다. 순수 모델의 보고는 실제 실행 증거와 구분한다.

Codex를 첫 지원 provider로 구현한다. Claude provider는 같은 계약에 맞춰 실행 프로필·격리·stream adapter를 검증한 뒤 별도로 활성화한다. 두 CLI가 설치돼 있다는 사실만으로 인증 상태나 작업 수행 가능 상태라고 보고하지 않는다.

### CLI 실행과 작업 결과 반영

2026-10-13 로컬 읽기 전용 조사에서 Codex 0.162.1과 Claude Code 2.1.296이 설치돼 있음을 확인했다. Codex 도움말에는 `exec --json`, `--output-schema`, `--output-last-message`, `--sandbox`가 있고, Claude 도움말에는 비대화형 `--print`와 `--output-format stream-json`이 있다. 실제 에이전트 작업이나 인증 변경은 실행하지 않았다.

불변 host runner가 고정한 executable·CLI 버전·프로필로 비대화형 프로세스를 시작한다. 셸 문자열 결합을 하지 않고 승인한 작업 명세를 stdin으로 전달한다. 현재 실행 중인 Codex/Claude 세션을 resume하거나 `--last`로 고르지 않는다. 새 전용 작업과 정확한 session ID를 기록하며, 재개는 그 작업 소유·범위·시간 제한이 검증된 경우에만 허용한다.

CLI가 호스트 기본 설정의 무제한 권한을 상속하지 않도록 승인된 전용 프로필을 사용한다. `danger-full-access` 또는 승인·sandbox bypass flags를 이 기능의 권한 근거로 사용하지 않는다. OS 수준의 파일·명령·네트워크 경계와 등록된 broker 접근을 실제 시험하며, 프롬프트에 적은 경로 제한 또는 CLI의 cwd 설정만으로 격리를 주장하지 않는다. 모델 연결에 필요한 인증은 host runner가 검증한 참조를 사용하고 채팅·작업 명세·공개 이벤트에 넣지 않는다.

다른 세션의 미커밋 변경을 보존하기 위해 작업 시작 시 현재 레포의 허용 입력과 변경을 스냅샷으로 고정해 전용 작업 공간에 제공한다. Git HEAD만 checkout해 사용자의 작업을 누락하지 않는다. 승인한 일반 코드 파일의 결과는 시작 시점의 바이트와 현재 파일을 비교해 충돌이 없는 범위에서 반영한다. 범위를 벗어난 파일·고위험 제어 파일은 검토 대상으로 보고하고 자동 반영하지 않는다. 충돌 시 reset·stash·기존 파일 덮어쓰기를 하지 않는다.

이미 편집 중인 레포·파일과의 동시성은 기존 프로젝트 잠금 및 입력 지문으로 조정한다. 호스트 작업은 별도 target lock을 사용한다. 에이전트가 만든 SQL·Docker 입력 역시 기존 소스 검토와 백업·013 보호 계약을 통과해야 하며, 에이전트가 작성했다는 사실은 승인 근거가 아니다.

### 사용량과 관찰

실행 프로필은 CLI provider와 명시적인 model ID·추론 설정을 고정한다. 채팅 모델이나 채팅 추론 레벨에서 에이전트 모델을 추정하지 않는다. CLI가 실제 모델·usage를 보고하지 않으면 `unknown`을 표시하며 설정값을 실제 관측값처럼 보고하지 않는다.

Codex 호출은 추가 모델 사용을 발생시킨다. ChatGPT 로그인은 해당 계정의 ChatGPT/Codex 사용 한도, API key는 Platform API 사용량·과금 경로를 따른다. 항상 별도의 구독 한도가 생긴다는 뜻은 아니다. 정확한 비용·잔여 한도를 추측하지 않는다. CLI가 제공하는 usage와 실행 시간을 집계하며, 계정별 hard token·금액 제한을 보장한다고 주장하지 않는다. hard budget이 필요한 프로필은 해당 provider의 강제 제한 기능을 검증하기 전에는 활성화하지 않는다.

JSONL/stream events는 허용 필드만 추출해 `source_kind=codex-cli|claude-cli`, 전용 actor/task ID와 연결한다. 작업 단계·편집 파일의 안전한 상대 경로·검증 상태·usage·승인 대기·완료를 대시보드에 표시한다. 전체 프롬프트·CLI transcript·추론·원시 stdout/stderr를 MCP 결과나 공개 감사 로그에 넣지 않는다. 원래 채팅 내역 대신 승인된 최소 작업 명세만 전달한다.

사용 한도 초과·인증 실패·CLI 미설치·모델 비가용·timeout·취소는 정확한 상태와 제한 사유로 보고하고, 다른 provider/model로 자동 전환하지 않는다. 에이전트 종료가 이미 진행 중인 Docker·DB 작업을 취소하거나 원복했다는 뜻은 아니다. 그런 작업은 기존 operation ID로 조회하고 불확실한 효과를 별도 확인한다.
