# PRIME Z690-P D4 BIOS 및 Intel ME 업데이트 절차

- 최종 확인일: 2026-09-11 / **갱신: 2026-10-19** (09-14 검토 결정의 반영 누락 2건 수정)
- 상태: **업데이트 대기 — 사전 준비 미완료. 아래 "착수 전 필수 선행 작업" 참조**
  (2026-10-19 재점검: 파일 자산은 전부 검증됨. 복구 USB·UPS 물리 준비 미완,
  당일 비정상 재부팅으로 중단 조건의 24시간 규칙 미충족)
- 추적 이슈: [#56](https://github.com/jhw7500/personal-ops/issues/56)
- 원칙: 호스트 작업과 BitBake 빌드가 모두 정상 종료된 유지보수 시간에만 진행한다.

## 대상 시스템

| 항목 | 현재 (실측 2026-09-14) | 업데이트 목표 |
| --- | --- | --- |
| 메인보드 | ASUS PRIME Z690-P D4 | 동일 |
| CPU | Intel Core i9-12900KS (family 6, model 151, stepping 2) | 동일 |
| BIOS | 1008 (2022-01-13) | 4003 (2026-06-08) |
| Intel ME | 16.0.15.1620/1624 | 16.1.40.2765 계열 |
| CPU 마이크로코드 | **0x3e (OS가 로드 중)** / BIOS 제공분은 0x18 | 아래 참조 |

ASUS는 BIOS 4003이 Intel 마이크로코드를 갱신하고 Intel ME를 16.1.40.2765로 함께 업데이트한다고 명시한다. BIOS를 나중에 롤백해도 ME 버전은 유지될 수 있다.

## 기대 이익 산정 (2026-09-14 실측 반영)

**릴리스 노트가 약속하는 이점을 그대로 계상하지 않는다. 이미 다른 경로로 적용 중인
항목을 빼고 남는 것만 이 업데이트의 실제 이익이다.**

```text
microcode: Current revision: 0x0000003e
microcode: Updated early from: 0x00000018
```

BIOS 1008이 공급하는 마이크로코드는 `0x18`이지만, Ubuntu의
`intel-microcode 3.20260210`이 부팅마다 `0x3e`로 덮어쓰고 있다.

| 계층 | 현재 | 4003이 바꾸는가 | OS 경로로 대체 가능한가 |
| --- | --- | --- | --- |
| CPU 마이크로코드 | 0x3e | 런타임 기준 사실상 이미 적용됨 | **가능 — 이미 하고 있음** |
| Intel ME | 16.0.15 (2022) | → 16.1.40 | **불가 — BIOS만** |
| FSP / PMC / 전력관리 참조코드 | 2022-01 수준 | 4.5년치 갱신 | **불가 — BIOS만** |

- 따라서 **"4003이 마이크로코드를 갱신하므로 비정상 재부팅을 고친다"는 추론은
  이 호스트에 대해 근거가 약하다.** [#57](https://github.com/jhw7500/personal-ops/issues/57)의
  비정상 재부팅 6회(2026-10-19 기준)는 전부 `0x3e`가 적용된 상태에서 발생했다.
- 이 업데이트의 **실제 남은 이익은 ME와 FSP/PMC 계층**이다. 공교롭게도 #57에서
  관측된 Fatal BERT 레코드가 SoC CrashLog(PMC가 기록)이므로, 그 계층의 4.5년치 갱신이
  증상에 영향을 줄 **가능성은 있다. 다만 인과는 입증되지 않았고 벤더가 이 증상을
  지목한 근거도 없다 — 가설로만 취급한다.**
- 마이크로코드만이 목적이라면 이 업데이트는 불필요하다. ME·FSP 갱신이 목적일 때만
  비용과 위험을 정당화할 수 있다.

## 착수 조건의 순환 — 먼저 해소할 것

- 이 작업의 목적은 "[#57](https://github.com/jhw7500/personal-ops/issues/57)의 하드 리셋
  조사 후속 조치"다.
- 그런데 아래 중단 조건에는 "최근 하드 리셋 원인이 계속 재현된다"가 있다.
- **두 조항을 함께 적용하면 어떤 상태에서도 착수할 수 없다.** 리셋이 있으니 올려야
  하는데, 리셋이 있으니 못 올린다.

현재 사실관계(2026-10-19 갱신): 비정상 재부팅은 6회다 — 09-11 16:50, 09-12 15:58,
09-12 21:09, 09-21 11:00, 10-12 15:02, 10-19 12:11. 앞의 3회는 약 28시간에 몰렸고 이후
간격은 9일·21일·7일이다. 직전에는 97일 무중단이었다. 6회 모두 Fatal BERT가 남았고
레코드는 동일 실패 모드다(#57 "BERT 레코드 대조" 절). 09-14 시점의 전제(3회·28시간
군집·39.5시간 무사고)는 더 이상 유효하지 않다.

**해소 기준 — 착수하려면 아래 중 하나를 명시적으로 선택하고 Issue에 기록한다.**

- **(A) 증거 우선**: BERT·rasdaemon·netconsole로 원인을 좁힌 뒤 BIOS를 결정한다.
  원인 규명에 유리하나 그동안 불안정이 계속된다. → **선택하지 않음**
- **(B) BIOS 우선**: ME·FSP 갱신에 베팅하고 먼저 올린 뒤 관측한다.
  빠르지만, 나아져도 왜 나았는지 입증할 수 없고 안 나으면 증거 없이 원점이다.

### 결정: (B) BIOS 우선 — 2026-09-14

**이 선택이 받아들인 것을 명시해 둔다. 나중에 "왜 이렇게 했나"를 되짚을 때 쓴다.**

- **인과 입증을 포기했다.** 재발이 멈춰도 BIOS 때문인지 증명할 수 없다. #57의 계측
  구성(rasdaemon·netconsole)을 먼저 넣지 않았으므로, 다음 재발 때 쓸 수 있는 증거는
  이번과 같은 BERT 레코드뿐이다.
- **롤백을 포기했다.** ASUS가 BIOS 2014에서 롤백 금지를 선언했고 현재 1008은 그 아래다.
  ME는 어떤 경우에도 복귀하지 않는다.
- **기대 이익은 ME(16.0.15 → 16.1.40)와 FSP/PMC 4.5년치 갱신뿐이다.** 마이크로코드는
  이미 OS가 `0x3e`로 덮어쓰고 있어 이 업데이트로 얻는 것이 없다. 관측된 Fatal BERT가
  SoC CrashLog(PMC 기록)라는 점이 이 베팅의 근거이지만, **인과는 입증되지 않았다.**
- ~~**UPS 없이 진행하기로 했다.**~~ → **2026-10-19 철회. UPS는 필수로 통일한다.**
  09-14의 이 결정은 같은 문서의 "착수 전 필수 선행 작업"·"중단 조건"·"사전 준비"가
  UPS를 필수로 두는 것과 정면으로 모순됐다(결정을 따르면 중단 조건에 걸린다).
  철회 근거: 비정상 재부팅 6회가 전부 11:00~21:09 KST 낮 시간대에 발생해 순간 전원
  단절 가설이 배제되지 않았고, UPS는 플래시 보호와 그 가설의 판별 실험을 겸한다.
  노출 구간은 플래시 5~10분이고, 재발 평균 간격(약 6일) 기준 그 구간의 재발 확률은
  약 0.1%로 추정한다. **그래도 이 판단이 틀리면 대가는 보드 사망이다** — CrashFree
  BIOS 3 실패 시 칩 교체.

**판정 유예**: 48~72시간 무사고로 해결을 선언하지 않는다. 직전 군집 앞에 97일 무중단이
있었으므로, 그에 준하는 기간을 지나기 전에는 "해결"이라고 쓰지 않는다.

어느 쪽이든 **플래시 중 리셋이 벽돌화로 직결되므로 UPS 확보는 선택이 아니라 필수다**
(아래 사전 준비 참조). 순간 전원 단절 가설이 아직 배제되지 않았다.

## 착수 전 필수 선행 작업

**유지보수 시간이 아니라 지금 끝내야 하는 항목이다. 당일로 미루면 그 자리에서 막힌다.**

- [x] **BIOS 1008 → 4003 직행 가능 여부 확인** (2026-09-14 조사 완료)
      ASUS가 이 보드에 대해 요구하는 필수 경유 버전은 **없다.** 이 보드 BIOS 페이지
      28개 항목의 릴리스 노트 전문에서 `sequential`·`step by step` 0건이고,
      4003 노트에도 선행 요구 문구가 없다. ME도 수동 선행 업데이트가 불필요하다 —
      4003이 ME를 동시에 올린다("Updating this BIOS will simultaneously update the
      corresponding Intel ME to version 16.1.40.2765").
      ASUS FAQ 1044348 은 일반론으로 *"Without any special Reason, no need to update
      each version, just update to the latest version"* 라고 안내한다.
- [x] **BIOS 4003 다운로드 및 해시 검증 완료** (2026-09-14)
      `~/host-bios-update-prep/bios/` 에 준비됨. 아래 "다운로드 및 검증" 참조.
- [x] **복구용·롤백용 CAP 확보 완료** — 아래 롤백 제약을 먼저 읽는다.
- [ ] **복구 USB를 물리적으로 만든다.** 이 보드는 **BIOS FlashBack을 지원하지 않고**
      `CrashFree BIOS 3`만 있다. 복구하려면 USB 루트에 CAP 파일이
      `PZ690P.CAP` 또는 `ASUS.CAP` 이름으로 있어야 한다.
      **플래시가 실패하면 이 PC가 죽어서 복구 USB를 만들 수 없다.**
      본작업용 USB와 별도로 2개를 준비한다. → `scripts/host-bios-usb-prep.sh`
- [ ] **UPS 또는 검증된 안정 전원을 확보한다.** 순간 전원 단절이 미배제 가설이므로
      이 항목은 "가능하면"이 아니라 필수다.

### ⚠ 롤백 제약 — 이 업데이트는 사실상 비가역이다

조사 중 확인된 내용이라 별도로 둔다. **4003으로 올리기 전에 이 제약을 받아들일지
결정해야 한다.**

1. **ASUS가 BIOS 2014(2022-10-19)에서 롤백 금지를 선언했다.** 해당 릴리스 노트 원문:
   *"Many ME updates and optimizations for the next-gen CPU are included.
   **This version does NOT allow rolling back to the previous versions** to ensure
   better compatibility."*
   현재 BIOS 1008은 이 선언선(2014)보다 **아래**에 있다. 즉 4003으로 올리면
   **1008로의 복귀는 ASUS가 차단한다고 명시한 범위에 들어간다.**
2. **ME는 영구적으로 되돌아가지 않는다.** BIOS를 낮춰도 ME 16.1.40.2765가 유지된다.

**추정**: 실질 롤백 하한선은 2014 이상일 가능성이 높다. 다만 ASUS가 "2014 이상만
가능"이라고 명시한 문서는 **찾지 못했다** (검색 범위: ASUS 지원 페이지 28개 항목 전문,
ASUS FAQ 1044348·1054166). 확인 불가 항목으로 남긴다.

**그래서 롤백본을 두 개 받아 뒀다.**

| 파일 | 성격 |
| --- | --- |
| `rollback/PRIME-Z690-P-D4-ASUS-3811.CAP` | **현실적 롤백 지점.** 4003 직전 버전(2025-11-21)이고 ASUS가 SHA-256을 게시한 몇 안 되는 버전 중 하나다. |
| `rollback/PRIME-Z690-P-D4-ASUS-1008.CAP` | 현재 버전. 2014의 롤백 금지 선언 때문에 **복귀 성공을 보장할 수 없다.** 보험으로만 둔다. |

되돌릴 수 없다는 전제로 결정해라. "안 되면 되돌리면 된다"는 이 작업에 적용되지 않는다.

## 소요 시간 견적

| 단계 | 시간 |
| --- | --- |
| 다운로드·해시 검증·USB 2개(본작업+복구) 준비 | 30~45분 |
| BIOS 설정 사진 + `efibootmgr -v` 저장 | 10분 |
| 정상 종료 + 냉각 | 10~15분 |
| EZ Flash 실행 (ME 포함, 자동 재부팅 수 회) | 5~10분 |
| Optimized Defaults + 설정 복원 + 저장 | 10~15분 |
| OS 부팅 + 버전·장치·온도 검증 | 10분 |
| **합계 (무사고 시)** | **약 1시간 15분 ~ 1시간 45분** |

플래시 자체는 10분 미만이고 대부분은 준비와 복원이다. CrashFree 복구로 넘어가면
+30분~수 시간, 최악의 경우 BIOS 칩 교체다. 위 "착수 전 필수 선행 작업"은 이 표에
포함되지 않는다(별도 시간에 미리 끝낸다).

## 중단 조건

다음 중 하나라도 해당하면 업데이트를 시작하지 않는다.

- BitBake를 포함한 중요한 작업이 실행 중이다.
- CPU 온도가 안정되지 않았다.
- **플래시 시작 전 24시간 안에 비정상 재부팅(PID 1 종료 마커 없는 종료)이 있었다.**
  결정 (B)에 따라 09-14까지의 조항 "최근 하드 리셋 원인이 계속 재현된다"는 이 구체
  조건으로 대체한다(원 조항은 목적 절과 순환해 어떤 상태에서도 착수할 수 없었다).
  재발 간격이 7~21일이므로 24시간 무사고는 안정의 증거가 아니라, 09-11~12처럼 28시간에
  3회 몰리는 군집 한가운데서 플래시하는 것만 피하는 최소 조건이다. 경과 시간은
  `scripts/host-bios-preflight.sh` 3절이 출력한다(현재 스크립트는 WARN으로만 표시한다).
- 정전 위험이 있거나 안정적인 전원을 확보하지 못했다.
- 메인보드 모델 또는 다운로드 파일의 해시가 일치하지 않는다.
- EZ Flash가 ME 호환성 또는 캡슐 검증 오류를 표시한다.

호환성 오류가 발생하면 강제로 진행하거나 임의의 중간 BIOS를 연속 설치하지 않는다. ASUS 지원에 현재 BIOS 1008 및 ME 16.0.15 상태에서 BIOS 4003으로 이동하는 공식 경로를 확인한다. Windows 환경을 사용할 수 있다면 ASUS의 해당 보드용 ME Update Tool 적용 여부도 함께 확인한다.

## 사전 준비

- [ ] 중요한 데이터를 백업한다.
- [ ] 실행 중인 작업과 BitBake 빌드를 정상적으로 완료한다.
- [ ] **EFI 부팅 항목을 텍스트로 저장한다** — `efibootmgr -v > <보관경로>/efibootmgr-before.txt`.
      BIOS 업데이트가 EFI 부팅 엔트리를 지우는 일은 흔하며, 사진보다 이 출력이 정확하고
      복원도 쉽다.
- [ ] **현재 BERT 상태와 마이크로코드 리비전을 기준선으로 남긴다** —
      `bash scripts/host-bert-collect.sh` 및
      `journalctl -k -b 0 | grep microcode`. 업데이트 후 재발 판정의 비교 기준이 된다.
- [ ] BIOS 설정 화면을 사진으로 남긴다.
  - 부팅 순서
  - SATA, VMD 및 RAID 설정
  - **`Restore on AC Power Loss`** — #57의 순간 정전 가설을 가르는 증거이며
    Optimized Defaults 적용으로 지워진다. **반드시 변경 전에 기록한다.**
  - Secure Boot 및 CSM
  - XMP
  - VT-x 및 VT-d
  - 팬 곡선과 CPU 전력 설정
- [ ] 불필요한 USB 장치, 특히 USB Wi-Fi 동글과 허브를 분리한다.
- [ ] **UPS 또는 검증된 안정 전원을 사용한다 (필수).** "가능하면"이 아니다 —
      순간 전원 단절이 #57의 미배제 가설이고, 이 보드는 BIOS FlashBack이 없어
      플래시 중 전원 이상에서 복구 여지가 좁다.
- [ ] FAT32 단일 파티션 USB 메모리를 **2개** 준비한다 (본작업용 + 복구용).
- [ ] 보드 이름이 정확히 `PRIME Z690-P D4`인지 다시 확인한다. `PRIME Z690-P`, WIFI 또는 DDR5 모델 파일을 사용하지 않는다.

### 이 호스트의 확인된 구성 (2026-09-14 실측)

복원 판단에 필요한 사실만 기록한다.

- **부팅 NVMe는 VMD 도메인 밖이다.** `nvme0n1`은 CPU 루트 포트 `00:06.0`에 직결돼 있고
  (`/sys/devices/pci0000:00/0000:00:06.0/0000:01:00.0/nvme/nvme0`), 두 번째 NVMe도
  PCH 루트 포트 `00:1a.0`에 있다. VMD 컨트롤러(`00:0e.0`)는 활성이고 도메인
  `pci10000:e0`를 만들지만 두 NVMe 모두 그 아래가 아니다.
  → **VMD 설정 변경이 곧바로 부팅 불가로 이어지는 구성은 아니다.** 그래도 원래 값은
  기록하고 복원한다.
- **Secure Boot 비활성, LUKS 미사용, TPM은 존재하나 디스크 암호화에 쓰이지 않는다.**
  → 펌웨어 갱신으로 디스크가 잠길 위험은 낮다.
- `/boot` 388 MiB, `/boot/efi` 505 MiB 여유 — 충분하다.
- 루트 파일시스템은 LVM(`ubuntu--vg-ubuntu--lv`) 위 915 GiB 중 162 GiB 여유(82% 사용).

## 다운로드 및 검증

BIOS 4003 ZIP의 ASUS 게시 SHA-256은 다음과 같다.

```text
771223DCF7832D633B69D69C6A62FB7A45BB89325E4269127D68C2C2CEE1E155
```

다운로드 후 확인한다.

```bash
rtk sha256sum <다운로드한_ZIP_파일>
```

**이 해시는 2026-09-11에 기록한 값이다. 다운로드 시점에 ASUS 페이지에서 게시 해시를
다시 읽어 위 값과 대조한다.** 두 값이 다르면 진행하지 않고 원인을 먼저 확인한다.

해시가 일치하면 ZIP을 풀어 `.CAP` 파일을 FAT32 USB의 루트 디렉터리에 복사한다. 정상적인 EZ Flash 업데이트에서는 BIOSRenamer로 이름을 바꿀 필요가 없다. BIOSRenamer는 주로 CrashFree BIOS 복구 절차에서 사용한다.

### 복구 USB (2번째 USB) — 같은 시점에 함께 만든다

이 보드는 **BIOS FlashBack을 지원하지 않는다.** 플래시가 중단되면 의지할 수단은
`CrashFree BIOS 3`뿐이고, 그것은 USB 루트에 정해진 이름의 CAP 파일이 있어야 동작한다.

```bash
# 두 번째 FAT32 USB 루트에, 같은 CAP 를 복구용 이름으로 복사
cp <추출한_CAP_파일> /media/<USB마운트>/PZ690P.CAP
```

- 파일명은 `PZ690P.CAP` 또는 `ASUS.CAP`이어야 한다.
- 롤백용 이전 버전 CAP도 이 USB에 함께 넣어 둔다(파일명은 구분되게 유지하고,
  복구 시에만 규정 이름으로 바꾼다).
- **이 USB는 플래시 시작 전에 완성돼 있어야 한다.** 실패 후에는 이 PC로 만들 수 없다.

## 업데이트 절차

1. 시스템을 정상 종료한 뒤 충분히 냉각한다.
2. **본작업용** USB 메모리를 후면 메인보드 USB 포트에 연결한다.
   (복구용 USB는 준비만 해두고 이 단계에서는 꽂지 않는다.)
3. 부팅하면서 `Del` 또는 `F2`를 눌러 BIOS에 진입한다.
4. `F7`로 Advanced Mode를 연다.
5. **플래시 전에 현재 설정을 기록한다.** 특히 `Restore on AC Power Loss` 값을
   반드시 남긴다 — #57의 순간 정전 가설을 가르는 증거인데 이후 Optimized Defaults로
   지워진다. 부팅 순서, SATA/VMD, Secure Boot/CSM, XMP, VT-x/VT-d, 팬·전력 설정도
   함께 촬영한다.
6. `Tool` > `ASUS EZ Flash 3 Utility`를 연다.
7. USB의 BIOS 4003 `.CAP` 파일을 선택하고 화면에 표시된 모델과 버전을 확인한다.
8. 업데이트를 승인한 뒤 완료될 때까지 기다린다.

업데이트 중에는 전원을 끄거나 리셋하지 않고 USB를 분리하지 않는다. BIOS와 ME 업데이트 과정에서 여러 번 자동 재부팅될 수 있다.

## 업데이트 후 확인

1. BIOS에 다시 진입해 BIOS 4003과 ME 16.1.40.2765 계열이 표시되는지 확인한다.
2. Optimized Defaults를 불러온다.
3. 운영체제로 부팅하기 전에 저장장치, VMD/RAID, 부팅 순서 등 필수 설정을 복원한다.
4. `F10`으로 저장하고 재부팅한다.
5. Linux에서 버전을 확인한다.

```bash
rtk cat /sys/class/dmi/id/bios_version
rtk cat /sys/class/mei/mei0/fw_ver
```

6. 유휴 상태와 부하 상태에서 온도 및 시스템 로그를 관찰한다.

## 완료 기준

- [ ] BIOS 버전이 4003이다.
- [ ] Intel ME가 16.1.40.2765 계열이다.
- [ ] 저장장치와 네트워크 장치가 정상 인식된다.
- [ ] 기존 운영체제로 정상 부팅된다.
- [ ] `efibootmgr -v` 결과가 사전 저장분과 일치하거나, 차이를 확인하고 복원했다.
- [ ] CPU 온도와 팬 동작이 정상 범위에서 안정적이다.
- [ ] **마이크로코드 리비전을 기록했다** — `journalctl -k -b 0 | grep microcode`.
      BIOS가 공급하는 값(`Updated early from:`)이 0x18에서 얼마로 올랐는지가
      이 업데이트의 실제 효과를 보여주는 유일한 직접 지표다.
      `Current revision:`은 OS가 덮어쓰므로 업데이트 전후가 같을 수 있다.
- [ ] 재부팅 후 새로운 BERT, MCE, xHCI fatal 오류가 발생하지 않는다.

### 재발 판정 기준 (#57 연계)

BIOS 업데이트의 성패는 "부팅이 되는가"가 아니라 **"Fatal BERT가 다시 나타나는가"**로
판정한다. #57에서 확인된 대로 BERT는 정상 종료 뒤에는 나타나지 않고 비정상 종료 뒤에만
나타나므로, 이것이 가장 직접적인 지표다.

```bash
# 업데이트 후 재발 시 즉시 실행 (읽기 전용)
bash scripts/host-bert-collect.sh
```

- 업데이트 후 첫 부팅에서 BERT 커널 메시지가 **없어야** 정상이다
  (직전 종료가 정상 종료였다면).
- 재발하면 새 `bert-region.bin`을 보존된 4건(`bert-20260912-2109`, `bert-20260921-121024`,
  `bert-boot-20261012-150428`, `bert-boot-20261019-121221`) 중 어느 것과든 `cmp -l`로
  대조한다. 구조(3444 B·3섹션·GUID)가 같고 Payload #1 차이가 #57에 기록된 클러스터 안에
  머물면 BIOS 업데이트가 이 실패 모드를 바꾸지 못했다는 뜻이다. 대조 방법은
  `docs/host-reboot-debugging-plan.md`의 "BERT 레코드 대조" 절에 있다.
- **48~72시간 재발이 없어도 원인 해결로 판정하지 않는다.** 직전 사건 군집은 28시간에
  몰려 있었고 그 앞에는 97일 무중단이었다. 무사고 기간만으로는 아무것도 입증되지 않는다.
  최소 97일에 준하는 관측 기간을 거치기 전에는 "해결"이라고 쓰지 않는다.

## 당일 실행 카드

**기기 앞에서 이것만 보면 된다. 플래시 중에는 SSH 가 안 되므로 휴대폰으로 열어 둔다.**

### 0. 재부팅 직전 (SSH 로)

```bash
bash scripts/host-bios-preflight.sh          # FAIL 0 확인
bash scripts/host-bert-collect.sh            # 기준선 (sudo)
```

본작업 USB(`BIOSUPD`, 4003 CAP)만 꽂고 **복구용 USB 는 옆에 두되 꽂지 않는다.**
Wi-Fi 동글·허브 등 불필요한 USB 는 뽑는다.

### 1. BIOS 진입

재부팅 → POST 중 `Del` 또는 `F2` 연타 → `F7` 로 Advanced Mode.

### 2. ⚠ 플래시 전에 반드시 기록 (사진)

**Optimized Defaults 를 적용하면 전부 지워진다. 여기서 안 찍으면 복구 불가다.**

| 항목 | 위치 |
| --- | --- |
| **`Restore on AC Power Loss`** | Advanced → APM Configuration — **#57 증거. 최우선.** |
| 부팅 순서 | Boot |
| SATA / VMD 설정 | Advanced → PCH Storage |
| Secure Boot / CSM | Boot → Secure Boot |
| XMP (D.O.C.P) | Ai Tweaker |
| VT-x / VT-d | Advanced → CPU / System Agent |
| 팬 곡선 · CPU 전력 | Monitor / Ai Tweaker |

### 3. 플래시

`Tool` → `ASUS EZ Flash 3 Utility` → USB 의
`PRIME-Z690-P-D4-ASUS-4003.CAP` 선택 →
**화면에 뜬 모델명이 `PRIME Z690-P D4` 인지, 버전이 `4003` 인지 눈으로 확인** → 승인.

> **이 시점부터 전원·리셋 버튼·USB 를 건드리지 않는다.**
> ME 업데이트 때문에 자동 재부팅이 여러 번 일어난다. 정상이다. 5~10분 기다린다.
> 화면이 꺼져 있어도 기다린다.

### 4. 플래시 후

1. 다시 BIOS 진입 → **BIOS 4003 / ME 16.1.40 계열 표시 확인**
2. `Optimized Defaults` 불러오기
3. **2번에서 찍은 사진대로 설정 복원** — 특히 SATA/VMD, 부팅 순서
4. `F10` 저장 후 재부팅

### 5. OS 복귀 후 (SSH 로)

```bash
bash scripts/host-bios-postcheck.sh
```

기준선과 자동 대조한다. 이 값들을 본다:

- `BIOS 제공 마이크로코드: 0x18 → ?` ← **업데이트가 실제로 먹었는지 보여주는 지표**
  (`/proc/cpuinfo` 의 `0x3e` 는 OS 가 덮어쓰므로 전후가 같다)
- `ubuntu 부팅 항목 존재` ← 없으면 `baseline/efibootmgr-before.txt` 로 복원
- `BERT 오류 레코드 없음` ← 있으면 정상 종료가 아니었다는 뜻

### 실패했을 때

**부팅이 안 되고 화면도 안 나오면** — 전원 끄고, 복구용 USB(`PZ690P.CAP`)만 후면
USB 포트에 꽂고 전원 켠다. CrashFree BIOS 3 가 자동으로 찾아 EZ Flash 로 들어간다.

**부팅은 되는데 디스크를 못 찾으면** — 설정 문제다. BIOS 에서 SATA/VMD 를
2번 사진대로 되돌린다. 디스크가 망가진 게 아니다.

**롤백하려면** — `rollback/PRIME-Z690-P-D4-ASUS-3811.CAP` 을 쓴다.
1008 로는 못 돌아갈 가능성이 높다(ASUS 가 2014 에서 롤백 금지 선언).

## 범위 제한

이 문서는 업데이트 준비와 수동 실행 절차만 기록한다. 실제 BIOS/ME 플래시는 별도 유지보수 시간에 사용자가 명시적으로 진행하기로 결정한 뒤 수행한다. 문서 작성 과정에서는 BIOS, ME, BitBake 프로세스 또는 빌드 캐시를 변경하지 않는다.
